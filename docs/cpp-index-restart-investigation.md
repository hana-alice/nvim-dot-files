## 原始调查结论与边界

现场的 `indexing 142/12456` 来自 clangd 的 background queue。今天 UEPrepare 完成后触发了

## 为什么没有压缩成少量 Unity TU

只读运行现有分组判据，1003 个 UBT unity wrapper 均未被采用：

- 995 组：完整语义 argv 与 response 内容不一致。
- 6 组：组内成员编译上下文不同。
- 2 组：部分成员不在当前 CDB。

Core 与 VulkanRHI 代表组中，active argv 包含额外 `-D__INTELLISENSE__`，原始 response 保留
已被 active 裁剪的 include 目录和 `.gch` 输入；Windows response 拆分另有一个开头空参数。
即使消除空参数，也仍有真实预处理输入差异，不能直接关闭上下文相等门禁来强行合并。

`lua/ue/index/_build.lua` 的进度文字仍称 “indexing uses super-unity TUs”，与本次实际产物不符。
本次仅调查并记录，没有修改该策略或文案。

## 缓存没有被清空，但仍不完整

单次目录采样共 17914 个 shard 文件，包含大量 header shard。对 CDB 中 basename 唯一的
16362 个 source 做保守匹配：4839 个有同 basename source shard，11523 个没有；其余179个
重名 source 不作断言。缺少同 basename shard 足以证明没有该 source 的标准缓存文件，
但“有同 basename”不单独证明路径/hash/内容均有效。

另一次稍后的采样中 18173 个 shard 里有15062个在今天之前创建，2742个在当前 clangd 启动后
写入。这证明旧缓存仍在、索引也在继续产出。采样会随后台工作变化，不能将11523硬等同于启动时12456。

本机版本 LLVM 22.1.5 的源码已交叉核对：

- [ClangdLSPServer.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.5/clang-tools-extra/clangd/ClangdLSPServer.cpp)
  用 `Completed - LastIdle` / `Enqueued - LastIdle` 构造进度；12456是本轮队列任务数，不是用户修改文件数。
- [Background.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.5/clang-tools-extra/clangd/index/Background.cpp)
  先恢复并校验已有 shards，再为需要更新的 TU 入队。队列包含加载/调度任务，不能把分母机械等同于独立 source 数。

## 2026-09-17：原生缓存补引用的可行性边界

缺失的 nonSpelled 引用不能忽略：独立原生实验确认它们会影响 references；function 类型的
相关记录还会影响 call hierarchy。小型模板实验把独立原 TU 已证明的一条 kind4 引用补入私有
RIFF refs chunk 后，完整图门禁通过，新 clangd 也返回该引用；其他 chunk 与缓存字节保持不变，
后台没有重新编译。这只证明记录能被消费，不证明缓存生命周期或性能收益。

真实 AIModule 的 owner-first 双 TU（53 个成员）重排后仍缺同一引用，证明耗时 118.42 秒。
补引用方案随后接受只读 donor 资格检查：第一个头文件的共同 266 个符号字段相同，但 donor
另有 8 个前向声明和必须保留的引用，不能用候选 shard 直接覆盖。下一个必需头文件
`DelegateSignatureImpl.inl` 的共同 261 个符号字段也相同，却存在一条 candidate 独有的 relation。
当前 refs-only 策略不能丢掉这个事实，也不能暗中扩展成通用符号/关系合并器，因此停止该候选
的生产推广；该后续检查只读两个 shard、129,344 字节，读取前后 donor hash/mtime 均未变化。
这是否定当前候选，不是所有合并策略均不可能的证明。

随后对此前未测的 AIModule 三个 UBT（60 个成员）做单路原生验证：原 TU 与候选均编译成功，
但完整门禁发现 `AITypes.h:305` 的 `GetTypeHash(ID.Index)` 调用引用缺失，kind28 包含
Spelled 与 Call，不能归入纯展示差异。拒绝记录保存后，辅助进程在序列化诊断图时触及设定的
3 GiB 上限并被资源守卫结束；全程 120.19 秒，没有有效 receipt。未运行仅对通过候选才执行的
共享缓存基线，也没有扩大资源上限、重试或发布该结果。

成本评估必须保留普通 warm cache、相同 donor 复制的原 UBT、prepared cache 三个对照。
两边后台编译均为零时仍可能有加载差异，但必须实测，不能把复制已有索引算成二次编译加速。
首次额外成本、每次净节省和同一有效输入期间的实际复用次数必须分别记录；实验重复次数不等于
用户实际复用，输入变化后不能继续累计旧证明收益。当前没有正的总成本收益证据，性能修复仍未完成。

live 22.1.5。两次小型实测中，原始命令有 15 symbols / 32 refs、零错误；PCH 加单独 header TU
仅有 13 refs、20 个错误，仍返回 exit 0，缺失 21 条原引用。相同符号数量和成功退出码均不代表
语义完整。该版本及 22.1.5 的 indexer 都调用清除 `ImplicitPCHInclude` 的
[同一初始化函数](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.5/clang-tools-extra/clangd/indexer/IndexerMain.cpp#L90)，
因此没有把这个失败实验扩大到 UE。两次合计 0.633 秒，原 fixture/PCH 字节保持不变。

## 2026-09-17：保存源码时的大 CDB 主线程阻塞

### 冷子集查找的后续修复

## 2026-09-21：Windows 文件名大小写的空 shard 根因与真实 Test 工程

已独立证实一个头文件丢符号机制，**不能据此声称历史 652 个目标 ID 全部已恢复**。
stock clangd 22.1.5 的 SymbolCollector 保留 include 中的文件名拼写，IncludeGraph 使用
物理文件名；Windows 上 `header.h` 与实际 `Header.h` 可以打开同一个文件，却得到不同
的索引 URI。FileShardedIndex 按 URI 分组，而 BackgroundIndex 只写 IncludeGraph 的 URI，
于是实际头文件的 shard 可以为空。小型原生对照中，逐文件原位 VFS 保留真实外部文件名后，
同样的源码/CPP 引用从缺失头符号恢复为 3 symbols / 5 refs，均零编译错误。

只更新 CDB 仍不足以修复历史缓存：保持原目录及三个旧 shard，加入正确 overlay 后的原生
热运行没有任何 `Indexed`，空头仍然为空、三个 shard 的 SHA 全部不变。只备份并移出
那个已确认的空头 shard，再运行则仅重索引一个 TU，恢复 3 symbols / 5 refs；其他两个
shard 字节不变。缓存迁移必须作为一次性正确性修复记录，不能把它包装成性能优化，
也不能推广为无条件清缓存。

## 2026-09-22：共享状态 revision 的并发写入

组合回归多次在 `state.revision.json` 原子替换时报告 EPERM。四个独立 writer 各执行
400 次完整临时文件写入、关闭及替换，没有 reader，仍出现 134/1600 次 EPERM；因此
“仅是 JSON reader 占用”的推断被证伪。当前 libuv Windows 实现调用
`MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`，见
[libuv 1.50.0 源码](https://github.com/libuv/libuv/blob/v1.50.0/src/win/fs.c)。

最初复用已完成临时文件、只对 EPERM/EACCES 即时重试至多 8 次，专项 23/23 通过，
但最终组合回归 **2068/2069** 在新增的持续并发用例再次失败。该方案已被证伪，不能
继续增加重试次数或把一次专项绿灯当成修复完成。真正的字段已经按 key 独立原子发布，
共享 revision nonce 却重新引入了所有 writer 的同一写入热点。后续修复应从这条数据
所有权边界入手，并继续验证跨进程缓存失效和实际文件替换失败的传播。

最终实现删除两处共享 nonce 写入，`project_state.read` 返回状态及同次原文采样生成的
稳定签名；缓存检查使用权威字段签名。这样各字段仍独立原子发布，后写的其他字段
不再争用 revision 文件。签名含有序路径和实际 JSON 字节，字段增加、删除、target pair
变化及同大小同 mtime 换内容均能失效。缓存建立直接保存同次读取的签名，防止把旧
状态配上后读的新 token。旧 `revision_path` 仅保留兼容，现有旧文件不删除、不再写入。
该机制不承诺多个独立字段组成一个原子事务，同字段替换失败仍明确返回错误。
