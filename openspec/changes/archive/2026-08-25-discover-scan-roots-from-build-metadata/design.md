## Context

见 `proposal.md` §Why（嵌套布局下 anchor 把扫描范围钉死在单一子树内，导致同层模块结构性不可见；
歧义布局回退根级把工具链拖进索引）。设计层面只需锁定这些既有事实：

1. **单一收口点**：`CORE_RT.project_index_dirs(ctx)`（`lua/ue.lua:2053`）是扫描根的唯一来源，
   10 个调用方（`3138`/`3609`/`3635`/`6440`/`8252`/`8334`/`8864`/`9167` …）全部经它取值。
   改这一个函数即可让全部消费方透明受益，无需逐点改造。
2. **缓存身份已就绪**：`project_scan_roots_match`（`lua/ue.lua:2099`）已被
   `lua/ue.lua:2403` 用作缓存复用前置条件，且 `8334`/`8864` 会把扫描根写回持久状态。
   扫描根一变，缓存自动判不可复用 → 一次刻意重建。**本设计不需要新增失效机制。**
   实测当前 bucket 的 `project_scan_roots` 为 `nil` → `match(nil)=false`，即旧缓存本就会被拒。
3. **返回值契约**：现行返回的是**项目根相对目录名列表**（`{"Source","Plugins",…}`），
   由 `existing_relative_dirs`（`lua/ue.lua:1864`）过滤掉不存在项后交给枚举器。
   推导结果必须沿用同一形态，否则 10 个调用方全部受影响。
4. **`SCAN_EXCLUDES` 已是正确的**：`Intermediate`/`Binaries`/`Content`/`DerivedDataCache` 等
   排除项经核对无误（cdb 里 4662 条 `Source/<Proj>/Intermediate` 命中属预期，不是漂移）。
   推导必须复用它，而不是另立一套排除表。

约束（`docs/CONSTRAINTS.md`）：不引入新依赖；P6 不阻塞主线程；优先结构化 API 而非 regex；
公共 API 挂 `M.*` 且 headless 可测。

## Goals / Non-Goals

**Goals:**

- 扫描根由 UE 构建元数据**推导**，新增模块目录无需人工干预即可被索引。
- 推导成本有界且可度量（实测 10ms / 333 目录，不随项目总文件数线性增长）。
- 只扩大覆盖、不缩小既有覆盖 —— 本改动不能把「漏扫 A」换成「漏扫 B」。
- 兑现 `lua/ue.lua:2050` 已承诺但不存在的 `:UEReloadScanPaths`，并给缓存真正的失效入口。

**Non-Goals:**

- 不做 workaround：**不**通过给该项目写 `.ueprepare-scan-paths` 来绕过推导缺陷（用户明确要求）。
  白名单仍保留，但作为用户逃生门，不作为本 bug 的修复手段。
- 不改缓存布局、平台维度、freshness 指纹机制。
- 不改 `SCAN_EXCLUDES` 既有条目。
- 不追求「完美最小集」—— 覆盖完整优先于扫描量最优；宁可多扫一个模块目录，不可漏一个。
- 不解析 `.Build.cs` / `.uproject` 的**内容**（不做 C#/JSON 语义分析）；只用「文件存在」这一事实。

## Decisions

### D1：以「模块声明文件存在」为信号，不解析其内容

**选择**：目录内出现 `*.Build.cs` / `*.uplugin` / `*.uproject` 即视为「此处有可编译代码」。

**理由**：UE 的构建系统本身就是靠这些文件发现模块的 —— 复用同一真相源，语义天然一致。
解析内容（ModuleRules 的 `PublicIncludePaths` 等）需要 C# 语义分析，成本高、易碎，且
对「该目录要不要扫」这个问题没有额外信息量。

**否决**：解析 `.uproject` 的 `Modules` 数组。它只列本项目模块，不含插件与嵌套项目，覆盖不全；
且 UE 允许模块不在 `.uproject` 里显式声明。

### D2：从 cdb 反推被否决

**否决方案**：直接读 `compile_commands.json` 的 `file` 字段反推目录。

**理由（实测）**：cdb 有 16020 条，但项目侧前缀分布是
`Source/<Proj>/Intermediate` 4662、`Source/<Proj>/Plugins` 3974、`Source/<Proj>/Source` 19 ——
**绝大多数指向 `Intermediate` 生成物**，且 cdb 只覆盖「当前平台+配置**已编译过**」的 TU。
未编译模块、shader、Config 全部缺席。cdb 是「编过什么」的记录，不是「有什么代码」的声明；
用它定义搜索范围会漏掉未编译代码，方向性错误。

### D3：有界浅扫 + 前缀收敛，两处硬性保护

**参数**：`maxdepth = 6`，复用 `SCAN_EXCLUDES`。实测 depth 4/5/6 分别 4ms/7ms/10ms、
遍历 62/162/333 目录，选 6 以覆盖 `Source/<Proj>/Plugins/<P>/Source/<M>` 这类真实深度。

**收敛**：候选按前缀去重（A 是 B 祖先则只留 A）。实测 142 候选 → 1 个真实模块根。

两处**必须**的保护（均已实测确认必要）：

- **剔除根级 `""`**：标准布局的 `.uproject` 就在 `project_root`，若把 `""` 当扫描根，
  收敛会把一切吞成「扫全根」—— 直接引入 `Content/`（影视资源）、`.git/` 全量遍历，
  是比原 bug 更严重的回归。实测：`converge({"","Source/M1","Plugins/P2"})` 不剔除时得 `{""}`。
- **空结果回落默认**：仅根含 `.uproject`、无其它模块声明时收敛为 `{}`；
  空列表语义是「不扫任何东西」，必须回落到 `UE_CONST.PROJECT_INDEX_DIRS`。

### D4：与既有结果取并集，而非替换

**选择**：无显式白名单时，`最终 = 去重(既有 anchor/默认结果 ∪ 推导结果)`。

**理由**：这是本设计**唯一的安全护栏**。推导有其盲区（例如纯 shader 目录 `Shaders/` 不含
任何 `.Build.cs`，但默认列表里有它；Config 同理）。取并集保证：本改动**在数学上不可能**
缩小任何项目的既有覆盖，最坏情况是多扫一点。若改成「替换」，任何推导盲区都会变成新的静默漏搜
—— 那正是本 change 要消灭的故障类别，不能自己再造一个。

**代价**：扫描根可能比理论最小集大（例如同时含 `Source/<Proj>/Source` 与更浅的
`Source/<Proj>`）。可接受：`existing_relative_dirs` 会过滤不存在项，且枚举器对重叠目录去重，
只影响一次遍历成本，不影响正确性。

### D5：白名单仍是最高优先级、且**不**与推导合并

**选择**：`.ueprepare-scan-paths` 非空 → 完全等于它，不追加推导结果。

**理由**：该文件的既有语义是「显式声明即最终答案」，用于让用户**收窄**范围（877k→116k 那个
收益就来自收窄）。若合并推导结果，用户精心收窄的白名单会被自动放大回去，等于废掉该机制。
保持「显式覆盖 > 自动推导」的优先级，也让本改动**不影响任何已在用白名单的项目**。

### D6：`:UEReloadScanPaths` 兑现而非删除

`lua/ue.lua:2050` 注释承诺了该命令，实际不存在，且 `project_index_dirs_cache` 无任何失效点
（会话内改布局/改白名单都不生效）。两种处置：删注释、或兑现命令。选**兑现** —— 因为缓存确实
需要失效入口（布局会变、白名单会改），删注释只是让文档不说谎，不解决可用性问题。
命令语义：清空 `project_index_dirs_cache` 与 `project_module_anchor_cache`（后者同样被缓存
且影响推导输入），随后下次查询重新推导。

### D7：不用 fd/rg 外部进程做发现

**选择**：用 `vim.uv.fs_scandir` 手写有界遍历。

**理由**：不引入对外部工具的新依赖（C 系列约束）；`fs_scandir` 在 depth≤6 + excludes 下
实测 10ms，无需子进程；且避免 Windows 上 fd 的 glob/引号差异（`shell-command-planning` 的既有坑）。

## Risks / Trade-offs

- **[推导把不该扫的目录纳入]** → 复用 `SCAN_EXCLUDES` + depth 上限 + 剔除根级；
  spec 已固化「排除目录不产生扫描根」与「歧义不回退根级」两个 scenario 作为回归守护。
- **[扫描根变多导致 prepare 变慢]** → 并集只增加目录条目，不改变文件级去重；
  真实项目实测收敛后仅 1 个根。若某项目确实被放大，用户可用 `.ueprepare-scan-paths`
  显式收窄（D5 保证它优先）—— 这是该机制的正当用途。
- **[全项目一次重建]** → 扫描根进入缓存身份必然触发一次重建，这是**刻意设计**而非缺陷
  （否则会静默复用按旧范围枚举的文件集）。用户体验为一次 `:UEPrepare`，且当前 bucket 的
  `project_scan_roots=nil` 本就会被判 mismatch，无额外损失。
- **[深度 6 仍可能不够]** → 已按真实布局（`Source/<Proj>/Plugins/<P>/Source/<M>` = 深度 6）
  选值。若未来出现更深布局，spec 要求的是「覆盖全部模块声明」，届时调深度即可，
  契约不变。为此需把深度做成命名常量而非魔法数字，便于调整与测试。
- **[并集使「最小扫描集」不可达]** → 有意接受（见 D4 代价段）。正确性优先于最优性。

## Migration Plan

纯运行时逻辑 + 新增命令，无数据格式变更、无缓存布局迁移。首次生效时用户会经历一次
`:UEPrepare` 重建（由缓存身份机制自动判定）。回滚 = `git revert` 单个提交；
回滚后扫描根回到旧推算，已建索引因 `project_scan_roots` 再次 mismatch 而重建一次。
